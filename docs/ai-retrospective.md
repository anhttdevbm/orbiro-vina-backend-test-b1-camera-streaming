# AI Retrospective

During the ORBRO B1 assignment, I used AI primarily through **Cursor IDE (Agent / Composer)** for architecture brainstorming, comparing RTSP-to-web streaming options, scaffolding the **Docker + MediaMTX + FFmpeg** local RTSP path, designing the **FastAPI camera CRUD API**, and reviewing **auto-reconnect** and status monitoring. AI helped me structure the system into clear components: RTSP source (looping `far.mp4`), per-camera **StreamWorker** threads with **OpenCV** ingest, **ChannelState** runtime metrics, the REST API and **WebSocket JPEG** transport, the **React** admin dashboard (grid, cameras, status, events), and a **psutil**-based monitoring module with optional NVIDIA queries.

AI was most valuable for mapping the assignment checklist to concrete modules quickly and for generating boilerplate—`docker-compose.yml`, worker loops, and admin pages—so I could focus on correctness and reproducibility. It also drafted **README**, **REPORT**, and **AI log** outlines, which I then edited against what actually ran on my machine.

However, I manually verified every important behavior in my local environment. I started the full stack with `docker compose up -d --build`, confirmed four streams in VLC (`rtsp://127.0.0.1:8554/cam1`) and on the web grid, exercised **camera registration and CRUD** via Swagger and the UI, and observed **connection status**, **FPS changes**, and **reconnect** by stopping and restarting an FFmpeg publisher. I ran `benchmark-metrics.ps1` for 30 seconds and recorded **real** CPU (~50%), RAM (~21%), per-channel FPS, and **~53 ms** server-side latency in `docs/REPORT.md`—I did not use AI-estimated performance figures. I also fixed issues AI did not catch: Windows **`DATABASE_URL`** conflicting with PostgreSQL (switched to **`CAMSTREAM_`** prefix), default RTSP URLs using **`mediamtx`** inside Docker instead of `127.0.0.1`, **`update_fps_only`** so FPS changes do not force RTSP reconnect, and a **PowerShell 5.1** bug in the benchmark script’s `Join-Path` usage.

Some AI suggestions were not directly suitable for this submission. For example, broader comparisons included **WebRTC** or **HLS** for lower latency or fan-out; I chose **WebSocket + JPEG** because it is simpler to reproduce in a one-command Docker demo and gives explicit server-side FPS throttling. AI discussed richer concurrency models; I kept **one worker thread per camera** for the four-channel demo while keeping the UI and API extensible to **32 channels**, and I documented that 32 simultaneous CPU decodes were not load-tested. GPU metrics were not reported as utilized: my laptop has an **RTX 4050**, but the backend container reported **`gpu_available: false`**, so the report states **CPU decoding only** rather than inventing GPU utilization.

Overall, AI accelerated design, scaffolding, and documentation, but **final architectural choices, code verification, performance measurement, and stated limitations** were checked manually. The submission’s value depends on reviewers being able to rerun the README steps, trust the benchmark numbers, and see honest trade-offs in the report—not on copying AI output without execution.
